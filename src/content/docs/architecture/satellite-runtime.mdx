Nobody logs in at the chalet. The Mac mini in the closet boots, waits for a key it cannot hold alone, and then keeps a family's curfews in a haus that is empty most of the week. Every job on it answers to the manoir. None of them can call it.

[Hive Topology](/architecture/hive-topology/) holds the rule: the hub opens every lane, and a satellite answers as data. This chapter is the inventory under that rule. It says what runs, who installed it, how the hub proves the bytes are still its bytes, and what the operator does when the box goes quiet. The audit behind it is in [The Manor Knocked a Hundred and Seventy-Four Times](/operations/2026-11-22-the-manor-knocked-a-hundred-and-seventy-four-times/).

## The lanes, all opened by the hub

Two lanes carry data through a forced command. The tunnels the hub dials each carry one narrow flow that starts on the satellite. A satellite still opens no connection of its own: the tailnet policy denies it every port.

| Lane | The hub's side | The chalet's side | What crosses |
|---|---|---|---|
| Screen gate | `screen_lane.py`, key `~/.ssh/screen-lane/chalet_ed25519`, the pinned host key, a post-quantum key exchange | forced command `/usr/local/libexec/sanctum/screen-gate` as `_sanctumgate`; gate 1.1 from K1 `p03` | one request line out; one JSON line back, checked against a pinned schema and printed as a fixed sentence. Twelve verbs |
| Fleet | `fleet_sync.py` every 15 min from `haus.sanctum.fleet-parity`, key `~/.ssh/fleet/chalet_ed25519` | forced command `/usr/local/libexec/sanctum/fleet-receiver`, and one sudoers line that restarts the engine | status as one JSON line; on drift, the hub's build out and a proved result back, or a rollback |
| Witness tunnel | `haus.sanctum.chalet-witness-tunnel` dials `-R 127.0.0.1:42071` and redials after 300 s | Vault Armor's boot unlock asks the hub's witness through it | one fixed-size curve point and a DLEQ-checked answer |

Gate 1.1 adds three verbs that only read. `devices` counts the chalet's devices by class and category since a given time, never a name or an address. `curfews` summarises the watchdog's enforcement ledger. `house` reports the Home Assistant doctor's verdict. Each answers `supported: false` until the file behind it exists, which is a refusal Yoda can say out loud.


## A boot that waits

1. launchd starts every system job. Nobody logs in, and with FileVault off no pre-boot prompt waits for a password.
2. `tailscaled` rejoins the tailnet and `com.sanctum.colima` starts the Home Assistant VM.
3. Vault Armor needs two witnesses: `chalet-fw` on the LAN, and the manoir's, through the tunnel the manoir dials. It retries once a minute until both answer. After the update reboot of 2026-11-22 the vault opened six and a half minutes after boot.
4. The engine and bridge launchers stop on an unreadable token, and launchd restarts them every ten seconds until the vault opens. That morning took 38 and 37 starts; then both came up with their tokens.
5. The watchdog records `vault_locked` in its ledger and kicks nothing while the vault is shut (K1 `p02`). Once the vault opens, its rows show the engine and the curfews again.
6. On the hub, the fleet sentinel's next pull sees parity, and thirty minutes without an answer pages.
   So do three curfew pulls in a row that find the engine answering while its loop has stopped or it reports enforcement not ready.

Every step waits or retries, and none gives up. November taught that: a one-shot unlock gave up after a reboot and left the vault shut for eight days.

## When it goes quiet

| Symptom | First look, from the manoir | Then |
|---|---|---|
| Fleet page: unreachable for 30 minutes | `fleet_sync.py status --site chalet` | Power, Wi-Fi, the tailnet. The curfews hold locally; only Yoda's view and commands are gone |
| Page: enforcement not ready during a curfew | lane `health`, then `curfews` | The bridge token the engine started with, its loop, then the watchdog's kicks in the ledger |
| Vault still locked after a boot | the witness tunnel's log on the manoir; witness 1's host key | Let the tunnel dial in. On site, the boot smoke's `--drill` with sudo ([Vault Armor](/architecture/vault-armor/)) |
| Floors `unavailable`, or `house` says `nuheat_reauth` | lane `house`, or the chalet's Home Assistant | Sign NuHeat in again in the chalet's Home Assistant; the link dies 30 days after each login |
| A root-owned file looks wrong | K1-check `--check`, with sudo for the root rows | `--rollback <phase>`, or rerun the phase |

<Aside type="caution" title="A kickstart is still not a heal">
The old watchdog logged `HEAL: kickstarted` 3,659 times, including kicks into a locked vault that could not possibly have healed anything. Its replacement re-reads the service after every kick and records what it saw. If the ledger shows kicks with no recovery, believe the ledger, not the word "heal". [Kickstart Is Not a Heal](/architecture/kickstart-is-not-a-heal/) has the doctrine.
</Aside>

## Hardening and its kits

The boundary design lists nine hardening steps, C1 to C9. They reach the chalet as kits: single Python files the hub emits from tracked sources, every payload pinned by sha256, run by the operator with sudo at the chalet. Every check runs before the first write, every phase backs up before it writes, and `--rollback <phase>` puts one phase back. Almost nothing goes on by hand. The exceptions are Home Assistant's loopback publication, at Monday's drill, and a few posture settings that need the GUI or a password.

| Step | What it closes | Kit phase | State |
|---|---|---|---|
| C1 | An sshd floor, `000-sanctum-boundary.conf`, with the post-quantum key exchange written out | K1 `p05` | Waits |
| C2 | Scoped sudo: the operator's blanket rule becomes a short list, installed last | K1 `p15` | Waits |
| C3 | The root watchdog runs root-owned code and writes the ledger | K1 `p02` | In place |
| C4 | Launchers fail closed on a missing token | fleet v1.1; K2 adds the wait loop | Partly in place |
| C5 | The engine stops trusting loopback callers | 1.0.1 | Waits |
| C6a | Home Assistant's VM mounts only its config | K1 `p11` stages it; the VM restart applies it | Waits |
| C6b | Home Assistant answers on loopback only | Q15, by hand at Monday's drill | Waits |
| C7 | Firewalla keys readable by the bridge only | K1 `p06` | In place |
| C8a | Sticky bits, and the engine's files owned by the engine's account | K1 `p07` | In place |
| C8b | The rest of the sticky bits, once the brain's write paths are checked | K2 | Waits |
| C9 | Root runs only root-owned code: Vault Armor, `tailscaled`, no dangling third-party daemon | K1 `p08`, `p13` on site, `p09` | Partly in place |

K1 is `chalet-kit-2026-11-22-install.py`, sha256 `b1a69fb6e840abd73219bed79d63df4036f4fb7967d33c418413aacd7993b59d`. Its verify-only twin, K1-check (`cd220ea9540260cb1815f4124370298b1585108a2c6d54aa30214cc8144bf962`), holds no write code. It ends `CLEAN pins=<hash>` or `DRIFT items=N`, and the hub keeps the pin hash, `c8d098a9b1dae784eaa0c888e2898a100dcb72d73d59749c7e6f577592ccf468` tonight. Until the fleet lane carries pins, K1-check after any OS update is the proof that root's files are still the kit's files. K2, this week, brings fleet v1.2, launcher v2 with the bridge under parity, the travelling screens and the floor reader.

## Exceptions, on purpose

Four things here are wrong on purpose.

| Exception | Why it stands |
|---|---|
| FileVault off | An unplanned reboot must not stop at a pre-boot prompt nobody is there to answer. The vault is its own encrypted volume; the data volume is not. Decided 2026-10-22, kept for 1.0 |
| The manoir's Share 2 lives here | The off-site witness share of the manoir's vault sits on that unencrypted data volume. One share opens nothing, and keeping it here is the operator's choice |
| Wi-Fi only | The Ethernet port has had no link, so every lane, the bridge and witness 1 ride Wi-Fi. Cabling it is an operator action on site |
| Parachute disarmed | No service copy of the [Parachute](/architecture/the-parachute/)'s key is on the chalet, so a curfew set while the Firewalla cloud is down will not land. It arrives with per-site Firewalla keys |

## What Deployed means on a satellite

On the hub, Deployed means the live file is the repo file, through a symlink into a gitsync'd checkout ([Engineering Discipline](/architecture/engineering-discipline/#eetismad--the-shipping-bar)). The chalet cannot read it that way. It holds no checkout of the config repo and must hold no hub credential, and root-run code has to be root-owned: a symlink into the operator's checkout would hand root to whoever can write there.

So the chalet uses a satellite reading, which still waits for the operator's sign-off. Every file the satellite runs is a byte-exact copy of a file at a named commit. Only a hub-built kit or fleet bundle installs it, pinned by sha256, and the hub re-checks it against digests it computes from that commit. A hand copy is not deployed, however right it looks. The check proves the absence of drift, not honesty: a compromised satellite can lie in its own checks, which is why the hub validates and the chalet only reports.

Today the fleet build meets that letter in full, through the 15-minute sentinel. Root's files meet it through K1-check until K2 moves their pins into the fleet lane.
