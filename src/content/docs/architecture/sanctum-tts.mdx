Yoda's voice answers the phone. Mothma narrates the morning briefing. Someday soon Neo's own digital twin does both, in English and in Quebec French, depending on who dialed. For any of that to be safe to put on a phone line that connects to the outside world, the TTS layer has to be two things at once: **clean enough that adding a new voice is a YAML edit**, and **boundary-enforced enough that an adversary who reaches the port can't impersonate someone**. `sanctum-tts` is that layer — one organ of [the Living Force](/architecture/living-force/), the haus's immune system, and the one that has to be trusted precisely because it speaks in someone else's voice.

## One Front Door, Many Backends

Every TTS engine brings its own Python environment, model format, and cloning quirks. Qwen3-TTS lives inside mlx-audio's venv. OpenVoice v2 clashes with it on torch/transformers pins. Coqui XTTS had its own world before we retired it. Keeping them in separate processes, each behind its own LaunchAgent, is the only sane way to add new engines without deps wars.

`sanctum-tts` is the Rust dispatcher on `:8008`. Callers ask for a voice by name; the daemon hands the request to whichever adapter the registry declares. Python never enters the dispatcher's process — adapters are thin HTTP proxies, kept in their own venvs the way you'd keep two cats in separate rooms.

<Aside type="note" title="Status: live on :8008 (post-quantum front door)">
The dispatcher is deployed and listening on `:8008` (launchd `com.sanctum.tts`), with post-quantum TLS in the crypto provider — hybrid X25519MLKEM768 key exchange, ML-DSA-aware, TLS1.3. It proxies via `QwenAdapter` to the Python voice engine on `:8011` (`com.sanctum.yoda-tts-worker`, now the Chatterbox `cbx-yoda` MLX model, not Qwen3). It serves both `/speak` and an OpenAI-compatible `/v1/audio/speech` shim, so existing callers were not broken at the cutover. Auth is permissive-localhost for now; the mTLS + ML-DSA-cert + Ed25519-signing hardening is the next step.
</Aside>

```

clients ──▶│ sanctum-tts  │──────▶│ cbx-yoda     │
 (mTLS)    │   :8008      │       │   :8011 (py) │
 Bearer ──▶│  dispatches  │──────▶│ openvoice    │
```

The `:8009` slot is the *intended* home for the OpenVoice worker — but right now that port belongs to the speech-to-text server (`workers.stt_server`). Standing up OpenVoice means either evicting STT first or picking a free port; the adapter still answers `NotImplemented` either way, so nothing collides until the day we wire it.

## The Five Layers

Every `POST /speak` passes through five independent defenses. Each is individually toggleable, so a laptop dev run can disable all of them while a phone-facing production deploy can demand every one. Layer 1 shares its certificate authority with the rest of the mesh — the same [mTLS migration](/operations/mtls-migration/) that hardened the council, reused rather than reinvented.

| # | Layer | Purpose | Stored in |
|---|---|---|---|
| 1 | **mTLS** | Cert-authenticated wire; same CA as `council-mlx`. | `~/.sanctum/certs/` |
| 2 | **Bearer-token ACL** | Per-voice authorization. Hashes only in config; plaintext lives with the client. | `tts.yaml` (SHA-256 only) |
| 3 | **Reference-clip pin** | SHA-256 of every voice's reference WAV. Mismatch at startup disables the voice. | `tts.yaml` per voice |
| 4 | **Ed25519 signing** | Every synthesized WAV carries a signed manifest (caller, voice, timestamp, text hash, audio hash). | WAV LIST/INFO chunk + HTTP header |
| 5 | **Hashed audit log** | Append-only JSONL; text is SHA-256'd before write so the log never becomes a surveillance vector. | `~/.openclaw/logs/tts-audit.jsonl` |

## What Each Layer Defends Against

<Aside type="caution" title="Adversary → defense map">
- Network access, no token → **401** (layer 2).
- Valid token for `yoda`, tries to mint Neo's voice → **403** (layer 2 per-voice ACL).
- Filesystem access, swaps `yoda-do-or-do-not.wav` for a stranger's clip → **503** at startup (layer 3).
- Captures a synthesized clip, replays elsewhere → the clip carries sanctum's signature. `sanctum-tts-verify` confirms origin; any "sanctum didn't produce this" claim is refutable.
- Fabricates a clip → no signature, `sanctum-tts-verify` exits 2.
- Tampers with audio bytes after signing → manifest's `audio_sha256` mismatches, `sanctum-tts-verify` exits 4.
- Asks "did caller X ever request voice Y with text Z?" → audit log answers. Plaintext of Z is never on disk.
</Aside>

## Signing — What It Proves, What It Doesn't

The signed manifest is canonical JSON with a stable field order:

```
{"v":1,"ts":"...","signer_id":"...","caller_id":"...","voice":"...","text_sha256":"...","audio_sha256":"..."}
```

Ed25519 over the UTF-8 bytes of that JSON. The signature + JSON both embed into the WAV as a RIFF `LIST/INFO` chunk (`ICMT` = manifest, `IART` = base64 signature). Clip travels, signature travels with it. Standard WAV readers ignore the chunk and play the audio; `sanctum-tts-verify` reads it and answers.

**What this proves**: any intact WAV came from a specific sanctum-tts instance (identified by `signer_id` = first 8 hex of SHA-256(pubkey)), with known caller/voice/text/timestamp.

**What it does not prove**: robustness to re-encoding. `wav → mp3 → wav` drops the RIFF INFO chunk; signature gone. The clip still sounds the same; we just lose the origin proof. Closing that gap needs a perceptual watermark layer (SilentCipher, AudioSeal) — deliberately scoped out of the MVP rather than shipped as handwritten theater.

## Operator Tools

```bash
# One-time: create the Ed25519 keypair at ~/.sanctum/keys/
sanctum-tts-admin keygen

# Mint a bearer token for a caller. Plaintext shown ONCE.
sanctum-tts-admin issue-token livekit-agent

# Compute SHA-256 for a reference clip to pin in tts.yaml
sanctum-tts-admin pin ~/.openclaw/tts-voices/yoda-do-or-do-not.wav

# Inspect the current signer
sanctum-tts-admin show-pubkey

# Verify a clip's signature + integrity
sanctum-tts-verify clip.wav
sanctum-tts-verify --json clip.wav
```

Exit codes of `sanctum-tts-verify`: `0` verified, `1` I/O, `2` unsigned, `3` signature invalid, `4` audio tampered after signing.

## Voice Registry

Add a voice with three YAML lines plus a pin:

```yaml
voices:
  yoda:
    adapter: qwen3
    reference: yoda-do-or-do-not
    language: en
    reference_sha256: 8f2a...  # sanctum-tts-admin pin
```

Adding Neo as a digital twin once OpenVoice v2 lands becomes two entries — `neo` (English) and `neo_fr` (Quebec French) — pointing at the same 2-3 min reference recording. The [voice-clone recipe](/operations/2026-06-28-voice-clone-recipe-annex/) is already written down; the only missing input is Neo standing still long enough to record it.
