### Root Cause Pattern

Every one shared a single failure mode: **the LaunchAgent got registered; the watchdog YAML did not.** The two-step was completed halfway, in three flavors:

1. **Service predates the YAML schema.** Force Flow and SanctumBridge got LaunchAgents before the manifest format existed. Nobody backfilled.
2. **Service fixed but not registered.** OBLITERATUS got its venv repaired last session; the fix closed the ticket and left the watchdog blind, because the focus was the Python interpreter, not the catalogue.
3. **Companion forgotten.** Memory-vault has a YAML; its paired reranker doesn't. Think of the two as one unit and you write one manifest.

The common thread: **the LaunchAgent is the developer artifact; the watchdog YAML is the operations artifact.** They live in different directories, get created by different people — sometimes different agents — with no gate between them. You can run a perfectly healthy, fully supervised service the watchdog has never heard of.

### The `catalogue-sync-check.sh` Guardrail

So a guardrail was born: `/Users/neo/Documents/Claude_Code/tools/catalogue-sync-check.sh`, to keep this class of drift from returning quietly. It does three things:

1. Queries the watchdog API (`/health`) for every port it tracks.
2. Runs `lsof -iTCP -sTCP:LISTEN` for every listening TCP port.
3. Cross-references the two, printing any port listening but not catalogued — filtered against a maintained ignore list of system ports (22, 80, 443, 631), macOS services (Raycast and ControlCenter on 5000, 7000, 7265), Cloudflare's internal listener (20241), and documented companion or internal ports.

After this session it outputs: `(none — catalogue is fully in sync)`.

**When to run it:**

- After any manual `nohup ... &` or `launchctl load` not accompanied by a service YAML commit.
- Before writing a [living-force](/architecture/living-force/) entry — it's the audit step that tells you what to write about.
- After a boot or LaunchAgent batch-load, to catch anything that came up without a manifest.

The `INTERNAL_PORTS` array is self-documenting: every excluded port carries an inline comment. Move a port off that list and it starts appearing in output immediately.

<Aside type="tip" title="The two-step registration will always try to drift">
LaunchAgents are a developer instinct. Watchdog manifests are an operational discipline. The guardrail script exists because the gap between the two is the exact shape most often missed at 11 PM.
</Aside>

## Gotchas for Next Time

- **Two-step registration is a trap.** Creating a LaunchAgent and starting a service is step one. Filing `~/.sanctum/services/<name>.yaml` is step two. The watchdog only sees step two. They are not linked. They will drift unless both are done in the same session.
- **HTTP-monitored services don't appear in the port sync check.** The watchdog health message says "HTTP 200" rather than "port X open" for services checked via HTTP (obliteratus, tommy, navigator-bridge). The sync-check extracts ports from the message text, so these don't show up as covered. They're tracked in the `INTERNAL_PORTS` ignore list with inline comments.
- **Companion ports need companion YAMLs.** If a service has a paired secondary port (reranker + memory-vault, livekit-server + token-minter), check whether the companion also needs a YAML. The fact that one half exists doesn't mean the other half was filed.
- **Bootstrap health-tunnel process.** On each boot, `sanctum-bootstrap.sh` may start its own health-tunnel with different port-forwarding args than the current on-disk plist. After running `sync_runtime_calibration.py`, always `launchctl unload` then `load` to replace the running tunnel with the new config. The bootstrap process will keep running with stale args until explicitly killed.
