The Gemini API key was minted, verified against a live endpoint, and written to SOPS. Seconds later it was gone, replaced by a key that had already been deleted at Google. The rotation reported success every time. So did the sync that destroyed it.

Four defects, none of which announced themselves. Each one alone would have been survivable; together they made it impossible for an auto-rotated secret to ever reach the login keychain.

## The direction rule

**SOPS is the source of truth. The login keychain is a derived cache.** Values flow one way:

```
rotate.py  →  SOPS store  →  login keychain
                          →  bare file consumer
```

Every defect below is a violation of that arrow.

## 1. The cache was rebuilt from itself

`sync-from-sops.sh` ended by calling `regen-keychain-sops-store.py`, which rebuilds the SOPS store **from the login keychain** against a hardcoded service list. Anything not on that list is dropped.

A freshly minted key, written to SOPS by the rotator, was therefore erased within seconds of the next sync — because it had never been in the keychain, and it wasn't on the list. The run reported `ok ... sops-store=refreshed`.

That script is a one-time migration tool that had been wired into the recurring path. It now carries a header saying so, and the sync no longer calls it.

## 2. A deleted secret on the airgapped VM won every time

The sentinel does not read the local vault. It opens an SSH connection to the VM and decrypts the VM's **own** copy.

That copy still contained a `gemini_api_key` from before the provider block was removed on 2026-07-26 — the *config* had been deleted, the *secret* had not. Because the lookup found a value there, it never consulted the Mini store, and every sync faithfully rewrote the keychain with a key that had been deleted at Google weeks earlier.

<Aside type="caution">
Removing a provider block does not remove the secret. Grep the vault, not the config, and confirm with the decrypted contents rather than the file you assume is being read. The first check here looked at the Mini's local vault and found nothing — the sentinel reads the VM's, over SSH. Same filename, different machine, opposite conclusion.
</Aside>

The key was verified dead (HTTP 400) before removal, then removed with `sops unset`: 25 keys to 24, everything else intact.

## 3. "Missing" was filed as "skipped"

One counter covered two very different outcomes:

| Outcome | What it means | What it was counted as |
|---|---|---|
| Keychain already matches SOPS | Nothing to do — healthy | `skipped` |
| Value not found in any store | **Unsynced. Broken.** | `skipped` |

Both exited `ok`. A custody sentinel whose entire job is propagating secrets was reporting green while propagating nothing.

`missing` is now counted separately and forces a `partial` verdict. It found defect 4 on its first run.

## 4. It worked over SSH and failed under launchd

With `missing` finally visible, the Mini store lookup was returning nothing — but only inside the LaunchAgent. The same script, same file, same user, worked fine over SSH.

launchd loads no shell profile, so `SOPS_AGE_KEY_FILE` was unset and `sops` could not decrypt. The key file is now passed explicitly rather than relying on the default search path.

<Aside type="note">
"Works when I run it, fails when the daemon runs it" is nearly always environment, not logic. A LaunchAgent gets no profile: no `PATH` additions, no exports, none of the shell's convenience.
</Aside>

## Verify the value, not the status word

The sync reported `written=0 skipped=6 failed=0` — all healthy. The keychain held a dead key at the time.

Status words are derived from the same broken logic you are debugging. The only check that settled anything was hashing the actual value in each store and comparing:

```bash
# GUI session — the keychain cannot be read over cold SSH
security find-generic-password -a sanctum -s gemini-api-key -w | shasum -a256 | cut -c1-12
```

Same twelve characters in SOPS, the keychain, and the file consumer, or it isn't synced. A second run must change nothing.

## The keychain is not a rotation target

`rotate.py` runs headlessly over SSH, where writing the login keychain **always** fails with exit 36, `errSecInteractionNotAllowed`. Listing the keychain as a rotation consumer only manufactured a permanent partial failure for work the GUI-session sentinel already does correctly.

The rotator writes SOPS and the file. The sentinel copies SOPS into the keychain, from a session that has the interaction rights. Rotation is now clean: two consumers, two ok.
