## 1. The Darwin Background QoS Throttle

Following our [previous socket draining fixes](/operations/2026-09-17-firewalla-bridge-socket-hang-and-healing/), the Firewalla REST bridge running on port 1984 resumed accepting connections. Yet under heavy midnight indexing, the bridge failed health probes anew. R2-D2 escalated an auto-heal failure:

```text
force-flow-bridge-sentinel: bridge process unreachable at 127.0.0.1:1984
r2d2: silent-failure escalation — bridge STILL UNREACHABLE after kickstart
```

Inspection of `/Library/LaunchDaemons/haus.sanctum.firewalla.plist` revealed the culprit. The launchd definition specified:

```xml
<key>ProcessType</key>
<string>Background</string>
```

Under macOS 27, Darwin strictly enforces background priority on daemons labeled with `Background`. The operating system assigned the bridge process to `TASK_APPLIED_DARWIN_BG` with priority `PRI: 4`.

When concurrent background tasks stirred at midnight, the Darwin kernel starved the bridge of CPU cycles, causing the single-threaded Node event loop to lag by more than thirty-one seconds while inbound TCP requests accumulated unanswered in the backlog. Because the process never returned to its poll phase, clients timed out before completing the HTTP handshake.

We purged the `ProcessType` key entirely from `~/.sanctum/launchagents/live/haus.sanctum.firewalla.plist` and re-installed the service. Launchd now spawns the daemon cleanly under standard system priority (`spawn type = daemon (3)`). Production health probes responded instantaneously at 1.4 milliseconds.

## 2. Jocasta CRM Mail-to-DuckDB Timeout Resilience

Less than an hour later, Jocasta fired a critical alert from `mail-to-duckdb.py`:

```text
Critical in mail-to-duckdb:
Traceback (most recent call last):
  File "~/.openclaw/workspace/scripts/mail-to-duckdb.py", line 374, in _osascript
    r = subprocess.run(args, capture_output=True, text=True, timeout=cap)
```

During large inbox syncs, AppleScript queries against the `Triptyq` exchange account exceeded the 240-second timeout ceiling. The script attempted a single retry, which also timed out.

Previously, `fetch_from_jxa` raised an uncaught `MailUnreadable` exception whenever any single account failed, instantly crashing the entire sync run, discarding cleanly fetched records from healthy mailboxes, and preventing any database updates from committing. Healthy mailboxes like Nepveu Exchange, Vrvana, and iCloud were aborted mid-flight.

We re-architected the retry handler to isolate failures per account:

```python
try:
    raw = _osascript(["osascript", "-l", "JavaScript", "-e", _jxa_script(acc, cutoff)])
except MailUnreadable as e2:
    print(f"  {acc}: JXA retry also timed out ({e2}) — skipping account this run")
    failed.append(acc)
    continue
```

The scraper now logs the lagging account, preserves records from sibling accounts, and commits them cleanly to DuckDB. An unhandled exception is raised only if every configured account fails simultaneously.

## 3. LinkedIn Browser Lock Eviction & Routing

A concurrent audit of the CRM fresh queue detected LinkedIn harvesting delayed beyond its 48-hour SLA window. Diagnostic inspection revealed an orphaned headless Chromium instance holding `SingletonLock` inside the profile folder:

```bash
pkill -f "user-data-dir=$PROF"
rm -f "$PROF/Singleton"*
```

We augmented `ingest/linkedin-sync.sh` with robust cleanup traps to evict orphaned browser processes and lockfiles before each harvest, while simultaneously retiring duplicate legacy crontab entries that competed with the native launchd service.

We also updated `scripts/proxy-route-e2e.py` in the configuration repository. Valid fallbacks to configured alternative models during upstream rate limits are now recognized without tripping false-positive CI alarms.

## 4. Tier-3 Autonomous Healing via Pi and Sanctum Brain

While deterministic sentinels and R2-D2 recipes quickly recover simple process crashes, compound failures previously dead-ended into midnight operator pages. To close this gap without relying on interactive developer tooling, we engineered an autonomous Tier-3 self-healing loop powered by the native `pi` coding harness and Sanctum's internal routing proxy. The loop is fully silent. Zero human intervention is required for recoverable faults.

When Tier-1 sentinels and Tier-2 kickstarts fail to restore port 1984, execution falls through to `~/.sanctum/scripts/heal-force-flow-pi.sh` rather than immediately sounding alarms. The script captures live telemetry—including thread samples, port bindings, launchd states, and recent error logs—into an incident snapshot before invoking the harness:

```bash
NODE_TLS_REJECT_UNAUTHORIZED=0 /opt/homebrew/bin/pi \
  --provider sanctum \
  --model claude-fable-5-1 \
  --no-approve \
  -p "$PROMPT"
```

Operating completely headless on the host, the agent diagnoses the failure against our SRE playbook, applies git-backed corrections, and verifies HTTP endpoints before yielding. Only if the autonomous agent cannot verify healthy responses does the system escalate to human attention.
