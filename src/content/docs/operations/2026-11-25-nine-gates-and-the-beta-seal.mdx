We could have bolted an override flag onto the gate and walked past it. We did not. One rule separates a real beta from a demo: you pass the gate you built, or you do not ship.

## Overnight verdicts: the G4 fused Metal LoRA engine

The build waiting at the door was G4 — `g3-fix` paired with the Stage-2 fused Metal LoRA kernel on [`sanctum-mlx`](/architecture/sanctum-mlx/). Earlier runs proved the LoRA weights made the local 27B brain smarter, then taxed decode speed to pay for it. Stage-2 fuses the LoRA side path directly into Metal for `1..=8` rows with a fused epilogue, bringing decode right back to base silicon speed.

## Gate 2b held — so we bumped to `mlx v0.32.5`

When Gate 2b halted the swap, the operator made the clean call: bump to `v0.32.5` and prove it instead of carving a backdoor around the check.

Three surgical edits landed in `sanctum-rs@e5e23d0`: the pinned `GIT_TAG` in `CMakeLists.txt`, `window_size = -1` in `fast.cpp`, and `IOKit` plus `CoreFoundation` in `build.rs`. No shortcuts. No skipped tests.

On the test node, `e5e23d0` cleared both fast trials back-to-back:

- **Trial of the Blade:** `53/53` LoRA coverage tests and `158/158` server tests passed with zero failures.
- **Trial of the Skirmish:** `SMOKE_PASS` in `218.9 s`, `496/496` live fused LoRA slots, `0` dropped, `25.47 tok/s` Stage-2 decode, and **`11/11` bit-exact SHA-256 and token parity** against the overnight `v0.32.4` champion.

Same answers, bit for bit. Fresh Apple Metal library (`mlx.metallib` SHA-256 `2f190f133101…`). Both `sanctum-rs` GitHub Actions workflows (`test` and `military-grade`) turned green, PR `#47` closed as merged, and `deploy-sanctum-mlx.sh` walked through all nine gates natively with zero overrides.

## Client first: locking port `:6669`

The same release hardened [Cilghal](/agents/cilghal/)'s loopback ablation seat on `:6669` behind mandatory token auth (`DEFAULT_ABLATION_PORT_REQUIRE_TOKEN=true`). Lock a server before its client holds the key and you break your own router. We deployed in strict order:

1. **Client binary first:** [`proxyd`](/architecture/proxy/) (`sanctum-rs@89806af`, `364/364` tests green) deployed live on `manoir` with zero downtime (`sha256 c37c0a18…`).
2. **Config and secret group perms:** `sanctum-config@203c050` landed `auth_token_file` and `auth_header: x-sanctum-ablate-token`, `sanctum-secrets-perms.sh --fix` tightened the token file to `0640` for the `sanctum` service group, and `proxyd` reloaded cleanly (`PID 76964`, all four providers healthy).
3. **Brain swap and negative proof:** `haus.sanctum.mlx` came up on `e5e23d0` (`PID 25732`, binary `04b03488…`, `CDHash ff83c878…`, `:1337` mTLS plus `:6669` loopback). Then `probe-ablation-health.sh --verify-auth` hit `:6669` twice: **`unauth=401, auth=200`**.
